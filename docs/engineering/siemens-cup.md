# 西门子杯：GD32F4 数据采集终端与 IAP 固件升级

## 项目背景

这是 CIMC 嵌入式赛项的作品：在 GD32F4 平台上做一个数据采集终端，要求能采集多路模拟量、按上位机的指令工作、把数据稳定地传上去，并且支持在线升级固件。

硬件外设不多，但要在一个固件里同时把采集、通信、存储、显示和升级五件事做稳，工作量比看起来大。

## 软件分层

```text
User/        main.c、中断、SysTick
Function/    业务逻辑、参数管理、采样封装
Protocol/    帧格式、CRC、命令解析
Driver/      ADC、AD3344、DAC、OLED、SPI Flash、UART、定时器
```

中断里只做最少的事（收字节进环形缓冲、置标志），所有业务都在主循环里按事件处理，避免长时间关中断影响串口接收。

## 采集与输出

| 通道 | 器件 | 用途 |
| --- | --- | --- |
| CH0 / CH1 | 片内 ADC | 模拟量采集，带比例系数换算 |
| CH2 | AD3344（SPI，16 位）| 接 PT100，读温度 |
| DAC | 片内 DAC | 输出设定值，掉电后恢复 |

采样走定时器：TIM6 以 50 Hz 触发 AD3344 采样，TIM2 以 1 Hz 推进心跳和上报计时。OLED 显示当前状态和采样值。

## 通信协议

自定义的二进制帧格式：

| 字段 | 长度 | 说明 |
| --- | --- | --- |
| 帧头 | 2 | `0xA5B6` |
| 设备 ID | 2 | `0xFFFF` 为广播 |
| 帧类型 | 1 | CMD / ACK / HEART |
| 命令字 | 2 | 见下表 |
| 数据长度 | 1 | 0 ~ 255 |
| 保留 | 1 | |
| 数据 | N | 多字节字段统一大端 |
| CRC | 2 | CRC32 低 16 位 |
| 帧尾 | 2 | `0xB6A5` |

常用命令：

| 命令 | 功能 |
| --- | --- |
| `0x0101` | 软件复位 |
| `0x0104` | 读固件版本 |
| `0x0105` / `0x0106` | 校时 / 读时间 |
| `0x0111` / `0x01A1` | 读设备 ID / 修改设备 ID |
| `0x0112` | 读 / 设波特率 |
| `0x0302` / `0x0303` | 启动自动上报 / 停止上报 |

解析时严格校验帧头、帧尾、总长度和设备 ID，任何一项不匹配就整帧丢弃，避免错帧进入业务层：

```c
if (header != 0xA5B6) return;
if (bin[len - 2] != 0xB6 || bin[len - 1] != 0xA5) return;
if (len != 9 + data_len + 2 + 2) return;
if (dev_id != 0xFFFF && dev_id != g_param.device_id) return;
```

自动上报时，一帧里打包 4 字节 RTC 时间 + 两路 float 采样值，间隔可选 1 s / 3 s / 5 s。

## 参数存储

参数（设备 ID、波特率、通道比例、报警阈值、DAC 设定值等）放在 Flash 的一页里，结构体带 `magic`、`structSize` 和 CRC。

直接写 Flash 有个风险：写到一半掉电，参数就废了。所以做了**双备份**：A/B 两个副本，读取时选 CRC 通过且版本较新的那个。

```text
0x08010000  参数主区
0x08010200  备份 A
0x08010600  备份 B
```

## Bootloader 与 OTA

固件分两段：Bootloader 固定在 Flash 起始，APP 区在偏移之后。上位机要升级时，先让 APP 写一个升级标记再复位：

```c
RTC_BKP1 = 0xA55A5AA5;   // 后备寄存器打标记
mcu_software_reset();
```

Bootloader 启动时检查这个标记，命中就进入 OTA 模式：

- 清标记、擦除 OTA 区域
- 一边解析协议帧，一边把固件字节写入 8 KB 缓冲
- 连续 500 ms 没有新数据，判定接收结束
- 整包 CRC32 校验通过后跳转到 APP

```c
typedef enum { OTA_IDLE, OTA_RECEIVING, OTA_COMPLETE } ota_state_t;
```

用「空闲超时」而不是固定长度来判断结束，是为了让上位机不用关心分包大小，最后一包什么时候发完都不会卡住。

## 主循环设计

```text
串口中断 ──▶ 环形缓冲 ──▶ 帧解析 ──▶ 命令处理 ──▶ 事件队列
                                                        │
主循环 ◀───────────────────────────────────────────────┘
```

命令处理不直接执行动作，而是往事件队列里丢事件（复位、开始/停止上报、LED 翻转、报警检查），主循环统一处理。好处是协议层不需要关心业务状态，也避免了在解析过程中做耗时操作。

## 踩过的坑

::: warning AD3344 的寄存器会被干扰
运行一段时间后温度读数会跳。最后的处理是每 30 次读取（约 3 秒）重新配置一次 AD3344 和外部参考，用一点开销换稳定性。
:::

::: warning 自动上报期间的命令冲突
自动上报时如果还允许改参数、复位，很容易把一帧数据发成两半。后来规定：上报期间只响应「停止上报」这一条命令，其余全部忽略。
:::

::: warning Flash 参数一掉电就没了
最早是单区写入，掉电测试必挂。改成 A/B 双备份 + CRC 之后，即使写到一半断电，至少还有一份完整参数可用。
:::

::: warning 帧长度算错
帧头长度按 8 字节算，实际是 9 字节，导致所有帧都校验失败。后来把 `9 + data_len + 2 + 2` 写成宏，只维护一个地方。
:::

## 结果

终端能稳定完成多通道采集、定时上报、远程参数配置和整机固件升级。相比功能本身，更有价值的是第一次把「协议—存储—升级」这条链路完整跑通。
